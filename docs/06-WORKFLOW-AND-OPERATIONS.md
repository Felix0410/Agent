# 06 · Codex 协作规范、上下文控制与运行部署

## 一、角色与工作节奏

用户负责产品范围和关键技术决策、审查、是否进入下一任务。
架构助手负责业务/接口设计、上游源码选择、任务书和验收复审。
Codex/本地 AI 负责在真实代码仓库内完成当前小任务、测试、Git 提交与真实结果报告。
单次仅一个任务包；完成后状态为 PENDING_REVIEW，未获得用户明确许可不继续 P 的下一包。

## 二、为什么要控制 AI 上下文

这个项目选择从零实现，就是为了避免直接修改 DeerFlow 庞大整仓的扫描/调用成本。保持单个任务的输入可控，长期信息靠文档恢复。

每次 Codex 只读：
1. README + docs/CURRENT_STATE.md（当前真实能力，不是全部远期愿景）；
2. 当前 Pxx 任务包，必要时 01/04 中相关模块的一小段；
3. 本项目相关 2～5 个源码/测试文件；
4. DeerFlow 对应 1～3 个上游文件（03 的具体路径）。
若必须扩大检索范围，先说明具体调用链与缺失信息，避免“全仓通读”。
任何新技术先讲是什么、为解决哪一具体业务引入、核心工作机制、替代方案和退出条件。

## 三、任务执行模板

- ID / 本次目标：可实际运行的最小用户行为。
- 现有能力/限制：引用 CURRENT_STATE 与 Git SHA。
- 本次范围与非目标：明确允许新增/修改的模块。
- 请求→执行→结果最小链路：成功、失败与边界。
- 核心接口/不变量：包括状态、权限、并发、外部副作用。
- 上游参考：最多 1～3 个确切文件和研究问题。
- 测试：Mock、集成、真实调用与安全回归分别列出。
- 交付：变更文件、命令结果、Git SHA、日志/产物、问题。
- 停止条件：验收失败、技术前提与实际代码冲突、安全越权等即暂停。
- 审核：用户批准才继续。

## 四、每阶段收尾文件

docs/CURRENT_STATE.md：建议小于几百行，只写当前实际系统的入口、目录、主数据流、已实现合同、运行命令、已知问题和最新 SHA。
docs/ARCHITECTURE.md：与真实代码同步，不用未来设计替代当前事实。
docs/DECISIONS.md：ADR（问题、选项、选择、代价、证据、何时回看）。
docs/PROGRESS.md：任务编号、状态、测试与 SHA。不得为每个细节重复开新文档。
docs/UPSTREAM_REFERENCES.md：确切参考文件与借鉴点及许可。
eval/：任务集、脚本和真实结果，不把大量 trace 复制进决策文档。

## 五、工程规则

- 模块化单体，不同时维护两个编排框架；调用现有 LangGraph/Tools 能力。
- 程序中强制工具 allowlist/timeout/最大调用数，不靠 Prompt 约束权限。
- 所有外部工具要支持确定性错误分类；未知副作用不盲目重试。
- API 层与领域层隔离；不允许 Route 里堆大段 Agent 工作流。
- 每次改代码先保护已完成的最小主线；重构要有回归和理由。
- 后台任务有终态和清理机制，避免内存泄漏、孤儿任务无限运行。
- 日志/Trace 包含相关 ID 与耗时/错误，不记录 API Key 和私人正文。
- Git 小提交、独立功能分支、无强制重写历史、保护未提交用户改动。
- 实际复制/修改上游 MIT 代码时要保留许可与归属；面试材料区分借鉴与自研。

## 六、环境与部署计划

P00 开发：
- Python 3.12+，版本由 lockfile 固定；安装运行 pytest/ruff 的最低环境。
- 仅 .env.example 入库，真实 Key 放 .env 并忽略。
- 真实模型 API 必须可切换且不写死供应商；不存在配置时清晰报错。

P02 状态：
- SQLite Checkpointer + RunStore；按异步编程方式选择正确 Saver。
- SQLite 单机有并发和锁限制，按当前单 Worker 使用场景设计；需要扩容再评估 PostgreSQL。
- 重要数据定期备份；数据库升级写迁移。

P03 文件：
- 工作目录及产物目录不提交；限制用户数据来源和输出大小。
- 上传与下载统一授权，路径/链接安全校验。

P07 Web：
- Next.js/React（具体版本到阶段确定），与 FastAPI 通过自有稳定 API 交互。
- 环境变量区分前后端，不暴露后端 API Key 到浏览器 Bundle。

P12 交付：
- 优先提供本地启动与 Docker Compose（一个后端/一个前端/可选数据库），根据实际依赖裁剪。
- 使用明确端口、Healthcheck、持久化 volume、启动顺序、容器非 root 权限。
- 敏感日志和上传数据不放公共展示仓库。
- 任意命令/代码执行只有在容器沙箱隔离及资源/网络/文件限制验证后开启，否则保持关闭。
- 不把“可以跑本地模型”当成高性能保证；模型响应能力受硬件和供应商影响。

## 七、质量门禁与 Git 发布

每个 Pxx 完成需证明：
1. 当前功能在全新环境能运行或明确记录阻塞；
2. 新增单元、集成和必要真实调用测试；
3. 主要 API/Tool/Run 合同无回归；
4. 文档 CURRENT_STATE 与 PROGRESS 更新；
5. 只有真实运行记录才算完成；
6. Codex 给出 Commit SHA 与未处理风险。
用户人工审核不通过则进入 BLOCKED/整改；禁止自动跳阶段。

## 八、优先保证学习价值

新技术教学优先结合实际代码说明流程；问“为什么不用其他方案”时必须做取舍而非仅列名词。每实现一项能力，就能从项目运行日志观察机制是否真正生效，并在项目中保留可解释的测试和设计选择。

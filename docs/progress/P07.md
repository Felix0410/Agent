## 最小可验证业务

用户提交研究问题 → Lead 使用 Todo/读取 `deep-research` Skill → `search_web` 搜索并保存真实 evidence_id → `fetch_webpage(evidence_id)` 经 Tavily Extract 取网页正文并记录“已提取/仅摘要/失败” → P04 Research 子代理按受限权限并行研究 → Lead 服务端校验 EvidenceStore 引用并调用 `save_research_report` → P03 Workspace 保存真实 Markdown Artifact → 轻量React ResearchPanel 显示来源和下载。未配置 TAVILY_API_KEY 时不假装在线搜索、不影响旧 P01–P06功能。

## 设计决策与原粗方案差异

1. 研究提供方只使用 Tavily Search+Extract 两个**固定 Tavily HTTPS API**。原粗方案允许 `httpx` 本机直接访问模型给出的任意 URL，SSRF/DNS rebinding 防线复杂；正式P07改为 `fetch_webpage(evidence_id)` 仅消费**当前 Run 已登记的搜索证据**，Tavily 作为第三方完成网页提取，本地 HTTP 只连固定Tavily API。无额外 Tavily SDK依赖，使用现有 httpx。
2. Research 子代理原P04不能联网，P07仅当用户配置了Key且实际Registry注册搜索工具时，赋予`search_web/fetch_webpage/list_evidence`三个**read-only**能力；General保持离线，任何Child不得write_text/报告生成/二次委派/MCP/Skills。Child启用P05 ToolGuard时移除原ChildToolBudgetMiddleware避免P06工具次数重复计数。
3. 证据不能靠模型杜撰：run-scoped业务SQLite真实记录搜索/提取的来源状态、URL/检索时间/正文有限摘录；Tavily提取不等于独立核真。报告的编号和 URL 由服务器根据 Evidence IDs 自动渲染，只允许同Run真实来源。查询每Run最多6次Search、8次Extract、30来源、1报告（SQL原子限额），另有P06 40模型/30工具/600s总额。
4. 已有 P06 `f291af58`“注释优化”提交确实在GitHub，但检查commit diff发现一处行尾多余空格、`main.py` import格式变化及一部分noqa删除；**P07-0编码前必须运行 git diff --check / Ruff check+format / 相关回归 / npm build**。失败时只在P07分支小范围格式修复后重新运行，不能假称现有基线lint已经通过。
5. 只读HTTP `GET /api/research/status`、`GET /api/runs/{run_id}/research/evidence`、`GET /api/runs/{run_id}/research/report`，外加轻量SSE，ResearchPanel沿用P03 Artifact下载及P06取消/Usage；前端不可直接发起Search/授予权限。

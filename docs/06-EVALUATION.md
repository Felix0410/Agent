# 06 · PaperWeave V2 测试、评测与消融协议

状态：**评测设计，尚无 V2 运行结果**。任何指标必须以真实运行、可重复语料和明确评分口径为依据。指标目标不等于完成值。

## 1. 为什么要双层评测

原版已提供论文入库、来源规划、检索契约和基本问答审查；V2 又增加知识构建层、科研任务层，因此应区分：
- **组件正确性**：解析、父子结构、索引、工具和状态是否符合合同。
- **研究任务质量**：选对论文、找对证据、正确抽取、有效比较、报告可信并完成任务。

检索命中不是答案正确；完整完成 Graph 不是研究成功；模型自评并非人工金标。所有报告同时披露样本量、来源、测试运行日期、模型和成本条件。

## 2. 原版基线（T01）

导入旧代码后固定一个上游 commit、依赖和已有可访问论文样本；执行现有 pytest、前端构建、API smoke、入库结构检测、来源边界、原版已知标题定位与问答契约。记录已存在失败，不为了“绿灯”修改业务代码。

上游公开的 46 篇论文库、5,467 chunks、已知标题 Hit@5 93.5%，以及 12 道中文检索 Hit@5、100 道问答契约仅作为**历史上下文**，不得直接继承为新仓库实际跑通结果。

## 3. BRAG 分层消融

| 配置 | 设计变量 | 作用与实验注意 |
| --- | --- | --- |
| E0 | 原版检索与索引 | 固定语料、模型、预算、硬负例 |
| E1 | E0 + B01 层级结构 | 若检索尚未使用层级，指标可持平 |
| E2 | E1 + B02 上下文/多视角索引 | 验证新增上下文是否改善召回 |
| E3 | E2 + B03 分层检索 | 验证选择论文/章节/证据层级的收益与开销 |

对照公平性：同一 query 集、语料 snapshot、Embedding/LLM、候选条数、Rerank 策略；记录差异参数。若某组新增加了 LLM 花费或候选量，必须单独报告额外成本，不能说免费提升。

检索样例至少覆盖：精确事实、指定章节、数值表格、图/算法、中文问英文、跨篇多证据、同名相似题、无答案问题、只有元数据无全文的外部结果。人工标注 gold document、gold evidence IDs 和许可范围。

指标建议：Document Hit@K、Evidence Recall@K、MRR/nDCG、Multi-evidence Coverage、Unsupported Citation Rate、Scope Violation、P50/P95 Latency、额外构建 Tokens/时延/存储、回退频率。

**评估原则**：重点展示“多证据科研查询”而非只用标题查找替代科研推理。对 E2/E3 无实证收益的配置允许禁用、回退。

## 4. Deep Research 任务评测

建议先构建 **10–20 个可复核小任务**（规划样本量，不是当前已有）：指定 2–3 篇本地论文为主，逐渐加入主题发现、缺失全文、冲突事实、不可比实验条件、工具失败和恢复。扩展数量必须在人工标注质量稳定之后。

每个 Case 至少有：输入目标和范围、必要论文/原文片段、预期事实字段、对比可比性判断、允许的结论、必须披露的缺口及执行限制。用领域研究人员人工审查部分样本，明示审查者和共识流程。

核心评分：
- **Literature Selection**：相关论文发现覆盖率、误选率、DOI/重复去重精度。
- **ResearchFact**：字段 Precision/Recall/F1；数值 exact match、单位/协议匹配；未知字段判定正确率。
- **Comparison**：同协议可比性判断准确率；不可比情况误排名比例。
- **Report**：研究任务要求覆盖率、Atomic Claim Supported Rate、引用有效率、重要不确定性披露率。
- **Execution**：端到端 Task Success（由外部固定规则/人工判定）、重试/恢复成功率、重复写入次数、取消正确率。
- **Efficiency**：LLM tokens/费用、工具次数、任务 P50/P95、缓存命中率；记录是否包含网络和入库时间。

## 5. 答案事实核验

当前上游的字面数字/相似度审查并非语义蕴含认证。V2 质量门建议按“原子事实→引用→原文支持判断”处理：
- 数字/单位/数据集/页码优先做确定性比较。
- 方法机制和研究结论必须检查上下文中的肯定/否定、适用条件与范围。
- 引用范围不合法、证据不足时要求补检索或清楚标记未核验。
- 自动审查器本身也要在人工标注集上报告误报与漏报，不能把 LLM judge 输出直接当绝对真值。

## 6. 稳定性与故障注入

| 故障 | 最低验收 |
| --- | --- |
| 网络/OpenAlex 超时 | 保留本地能力、披露外部不可用 |
| 全文不存在 | 保留候选元数据，不伪造研究事实 |
| Embedding/重排失败 | 有明确回退，旧索引可查 |
| 任务 Worker/API 退出 | Checkpoint 可重建，幂等恢复 |
| 同一个任务重复投递 | 不产生重复事实/报告破坏 |
| 中途取消 | 终止后续任务步骤并记录结果 |
| 模型返回无效结构化 JSON | Schema 校验失败，有限重试或可解释失败 |
| MCP 授权错误/不可用 | 研究主体继续，MCP 部分标记未验证 |
| 文档 Prompt Injection | 只当不可信研究资料，不执行越权操作 |

这些测试必须有自动化或清晰的人工复现命令，不能只写在报告里。

## 7. Trace 数据要求

记录任务 ID、运行/评测版本、步骤、工具名、调用时间、延迟、错误类别、简化输入/输出结构、证据 ID、Tokens/费用估计、重试次数；敏感字段脱敏/不存储。原文段落与用户内容不应无差别写入公开测试工件；私有数据集不提交公共仓库。

## 8. CI、回归与对照输出

每个任务包完成至少执行：其本身单测、公共旧功能回归、需要时 API/数据库集成；改动检索时同步跑固定检索套件；改动前端时跑构建与最小交互；改动长任务时跑故障恢复测试。若测试环境缺外部凭证，要分离 Mock 通过和真实集成未执行状态。

推荐产物：配置与 Git SHA、数据集 manifest、gold labels、逐 Case 结果、Trace/错误列表、汇总 Markdown/JSON。所有结果解释必须指出样本限制与统计不确定性。

## 9. 对简历结果的要求

只有本仓库可复现的实测结果才能形成数值化简历贡献。避免“提高 50%”、“百万论文实时处理”等未经验证表述。可写清楚技术因果链：做了什么 Build/Agent 改造，为什么，用什么对照组验证，对准确性与成本各有何影响。

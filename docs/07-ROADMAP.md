# 07 · Codex 独立任务包 / 依赖顺序 / 验收规则（最终版）

状态：设计已确认，任务**均未开始**。任务编号固定，开发实际文件与命令由 Codex 审计后决定。每次只提交一个任务，结束后人工审核与签收。

T00 → T01 → T02

**第二批：知识 Build（BRAG）**

**第三批：Deep Research 产品主线**

## 1. 每包共同交付格式

每包明确：目标、范围、非目标、验收、测试。Codex 应先检查仓库状态并读取 00–08 中相关文档；按实际代码选择最小改动方案；本包完成后提交单独 Git Commit，并更新 11-PROGRESS。输出真实测试命令/结果、变更文件、设计偏差和风险；**不要继续下一包**。

## 2. T00 — 上游来源与真实架构审计

**目的**：确认新仓库空文档阶段如何安全引入原 PaperWeave；识别原版部署、接口、依赖、许可、数据库和测试真实情况，形成可执行实现审计记录。

**任务范围**：阅读上游仓库、固定上游 SHA、确认许可证/归属、记录新仓库当前结构；核实 RAG Tool、API、会话、入库、Docling、检索、图谱、SSE、任务与数据库迁移机制；评估与目标架构差异。更新必要审计文档和迁移建议。

**非目标**：不改业务代码、不启动 B 层或任务 Graph、不删除设计文档、不覆盖工作区未提交内容。

**验收**：上游版本、目录/依赖图、接口复用列表、许可方案、源代码引入流程、环境阻塞和风险清单可追踪；描述哪些事实已验证、哪些待 T01 实测。给出下一包具体操作计划。

## 3. T01 — 引入原版 + 运行基线

**目的**：让本仓库成为可运行的 PaperWeave 衍生仓库，而非单纯设计仓库。

**范围**：按 T00 审核的方案从上游引入原版源码并保留许可证、版权及原版来源；**不覆盖现有 docs/ 文档**；固定依赖、构建/启动、测试及旧功能 smoke；运行可运行的现有回归和评测，保存基线快照。明确环境中尚不能真实运行的测试与理由。

**非目标**：不引入新的 Research Agent、Build 增强或依赖大升级；不擅自重写旧源码。

**验收**：仓库包含可审计原版代码和合法许可，旧功能能按说明运行，测试报告包含成功/失败/未运行分类，分支/commit/数据快照可复现。

## 4. T02 — 共享科研服务接口

**目的**：让独立研究任务图复用旧库能力，而不绑死 2,000 行级旧 Agent 实现。

**范围**：基于真实源码抽出薄 Adapter：列出/读取论文、真实章节、正文/Artifact 检索、OpenAlex、必要入库状态、引用转换。统一源信息和范围限制。加契约测试和旧版回归。

**非目标**：不重新实现 Embedding/Hybrid/RRF/Rerank；不碰旧 Planner 算法，不新增 Graph。

**验收**：可以脱离旧问答工作流直接调用共享科研接口；结果与旧底层语义一致；旧 API 兼容。

## 5. B01 — 显式层级知识构建

**目的**：在原 Chapter/Chunk/Artifact 基础上增加 Paper/Section/Evidence 的可追溯父子关系。

**范围**：增量构建、稳定 ID/原文映射、论文和章节概览（与真实原文标记区分）、版本与失败恢复。支持仅对单篇重建。

**非目标**：不重写 PDF 解析、不更换 DB、不做分层检索路由。

**验收**：论文—章节—原文/图表完整可查；重建幂等、旧索引安全；失败有回退，关键节点完整性有测试。

## 6. B02 — 上下文与多视角索引

**目的**：让语义查询能结合论文/章节上下文召回片段。

**范围**：source_text 与 retrieval_text 分离、上下文语义视角、关键词/可配置少量假设问题视角、缓存与版本/哈希、可关功能开关。

**非目标**：不全量无差别生成问题，不重写 RRF，不使用增强文本作原文事实。

**验收**：增量构建可重复、指标可记录、旧检索可回退；原文不变化；成本有上限。

## 7. B03 — 分层检索与 BRAG 消融

**目的**：Fact 查询直达证据、Overview/Comparative 查询按 Paper→Section→Evidence 逐层找原文。

**范围**：路由与参数预算、继承 Scope Policy、Hybrid/RRF/Rerank 协作、证据结果规范、原版开关与 E0–E3 对照评测。

**非目标**：不新增大量 Agent，不将图谱边作为事实，不为所有问题强制三层检索。

**验收**：E0 原版稳定；新层级可打开和回滚；各类查询范围正确；消融报告包含召回/费用/延迟与失败分析。

## 8. T03 — Research Task 模型与 API

**目的**：定义可追踪且持久化的研究任务对象。

**范围**：目标与 scope、候选/已选论文关联、步骤及状态、结果身份、合法状态转移、创建/查看/查询基础 API 与安全迁移。

**非目标**：不接 LLM、不跑长任务、不做前端。

**验收**：服务重启后任务与关联仍存在；非法转移/重复创建/外部越权被拒绝；数据迁移不破坏旧表。

## 9. T04 — ResearchTaskGraph 最小运行

**目的**：让“指定 2–3 篇已入库论文→分析→有证据 Markdown 概览”真正端到端完成。

**范围**：独立 Graph；调用 T02 接口；检索论文、写出分篇概况、综合结论、引用与执行状态；真实一组论文 smoke + Mock 单测。

**非目标**：不做自动搜索、不做正式字段矩阵、不做大规模并行 Agent、不做持久 Checkpointer（T08 补强）。

**验收**：真实任务有持久化产物，不能将随机文本当作成功；旧问答功能回归仍通过。

## 10. T05 — ResearchFact 结构化抽取

**目的**：为论文研究方法、实验协议、数据集、数字、限制建立可复用事实模型。

**范围**：字段模板、Structured Output、证据 ID、数值/单位/协议校验、缺失/不确定状态、抽取缓存、金标小样本。

**非目标**：不做比较报告、不向未知字段填假数据。

**验收**：单篇论文抽取可核验、可回读、可缓存；字段错误被检测且有测试。

## 11. T06 — 比较矩阵与报告

**目的**：让 Deep Research 交付跨论文结构化矩阵和可信报告。

**范围**：按事实字段对齐、数据集/协议可比性判定、研究结论核查、Markdown/JSON 导出、结果版本与出处。

**非目标**：不写 PDF 排版引擎，不将“模型猜测”作为已确认结论。

**验收**：同组论文可生成稳定产物；数字来源可追踪；不可比协议不产生误排名。这是首个完整业务里程碑。

## 12. T07 — 自动文献发现与人工确认

**目的**：从用户主题出发找到论文并衔接已完成分析主线。

**范围**：复用 OpenAlex/本地库、候选去重和来源身份、元数据与真实 PDF 区别、候选列表/确认点、合法开放全文入库、边界/预算。

**非目标**：不做无限抓取、无限自主搜索或未经许可全文下载。

**验收**：主题→候选→确认→已有研究链路成功；无全文场景不伪称完整阅读；重复论文不重复入库。

## 13. T08 — 长任务 Checkpoint / 取消 / 恢复

**目的**：可靠执行可中断研究任务。

**范围**：核实 LangGraph Checkpointer 的兼容版本；持久化 Run/Step 状态；区分数据库/MQ/Checkpoint；有界重试、取消、候选确认恢复、幂等、故障注入。

**非目标**：不新增第二个复杂编排引擎，不破坏现有入库 worker。

**验收**：故障后重启恢复且不重复写坏记录；取消不继续未授权行为；展示真实测试结果。

## 14. T09 — Research Tasks 前端

**目的**：从网页完成任务创建到阅读报告。

**范围**：独立入口，研究目标/范围、候选确认、真实进度、步骤和失败、研究矩阵、报告查看/下载、取消/恢复；复用原版 UI 风格。

**非目标**：不重做 PDF.js、知识星图、不使用虚假进度。

**验收**：网页完成真实任务；刷新数据不消失；错误/空/取消状态完整；前端构建与原版功能通过。

## 15. T10 — Golden Tasks / Agent Eval / Trace

**目的**：让新系统具有可复现的质量与工程结论。

**范围**：固定人工核验科研任务集、实验条件快照、任务完成/字段/引用/协议可比/成本指标；Trace、Bad Cases、对比 Markdown/JSON 产物。

**非目标**：不拿 LLM 自评冒充金标，不以看起来好看的仪表盘优先于可复现数据。

**验收**：测试样本可复跑；任务级成功与检索/契约被分开打分；失败可定位且指标有运行证据。

## 16. T11 — GitHub MCP Client（第二优先级）

**目的**：把论文关联代码仓库的元数据与静态复现条件纳入报告。

**范围**：只读 GitHub MCP、真实 Schema/连接/超时/错误处理、官方仓库确认规则、代码可获得性字段、任务降级。

**非目标**：不执行陌生仓库代码，不做全能 Coding Agent、不强制完成 MCP Server。

**验收**：至少一项真实研究任务调用 MCP 成功；鉴权失败/超时等情况主体报告仍可产生。

## 17. T12 — 最终集成、交付与来源声明

**目的**：使所有已完成模块能够稳定运行与展示。

**范围**：旧功能回归、端到端演示、权限/密钥/Prompt Injection/依赖检查、Docker 启动、文档与技术贡献归属核验、非预设成功数据的评测记录。

**非目标**：不借发布名义加入新的业务特性，不虚构数据。

**验收**：清洁环境可依说明部署；真实论文研究样例成功；已做模块有独立测试与出处；README 清楚区分继承/新增；产出项目说明与真实性能。

## 18. 阶段门槛与暂停规则

每阶段如有未通过验收或重大风险，不得自动进入下一包；用户提交 Codex 总结后由助手审核。B02/B03 若效果差可通过 ADR 关闭优化，但必须记录负结果。MVP 过程中已有功能不因重构而回退。T11 非 M1 核心交付依赖，时间不足允许延后。

## 19. 让 Codex 开始的方式

先指派 **T00**，要求只读核查与审计文档提交，不着手新增业务代码。T00 确认当前仓库是文档先行、尚无原版源码；T01 才安全迁移上游。后续每包的详细背景分别对应 01/02/03/04/05/06/08/09 文档，而不是一口气把全部实现计划交给 Codex 执行。
